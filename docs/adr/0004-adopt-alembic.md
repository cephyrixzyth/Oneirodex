# ADR 0004: Adopt Alembic for schema migrations

> **Doc status:** Active

**Date:** 2026-09-09
**Status:** Accepted — supersedes [ADR 0001](0001-schema-migrations-defer-alembic.md)
**Owners:** `agent-backend` · `agent-ops`
**Program:** modernization, wave A3.1

## Context

ADR 0001 deferred Alembic for 1.0. Schema was built by `db.create_all()` plus
`oneirodex/updateschema.py` — ~1700 lines of idempotent raw
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` run during `init_manager` Phase 2.
No revision history, no downgrade, no drift check: a model edit without a
matching `updateschema.py` change drifted silently, and CI could not assert
that models and schema agreed.

1.0 has shipped. The deferral's preconditions (no mid-release rewrite) no
longer apply.

## Decision

Adopt Alembic. Specifically:

1. **Baseline revision** (`alembic/versions/b9ab856b09ff_*`) — a squash of the
   schema `create_all` + `updateschema.py` produced. Autogenerated against an
   empty DB (so it is almost entirely `create_table` / `create_index`), then
   hand-extended with the indexes `updateschema.py` created that `models.py`
   never declared. A fresh `alembic upgrade head` reproduces the pre-Alembic
   schema exactly (verified with `pg_dump --schema-only`).
2. **`updateschema.py` is frozen.** No new DDL. It stays only to carry
   pre-Alembic installs up to the baseline. New schema change = a new Alembic
   revision.
3. **Existing installs** — `init_manager` Phase 2, after the `create_all` +
   `updateschema.py` pass, runs a one-time `alembic stamp head` when the DB has
   a schema but no `alembic_version` table. It never re-runs the baseline;
   failures are logged and swallowed so boot cannot break on it.
4. **`env.py`** resolves the DB URL the same way the app does
   (`DATABASE_URL` → `TEST_DATABASE_URL` → `config.Config`, or `-x db_url=`),
   targets `oneirodex.models` `db.metadata`, and runs with `compare_type` /
   `compare_server_default`.
5. **Drift gate** — `alembic check` is clean. A named allow-list in `env.py`
   (`_BASELINE_ONLY_INDEXES`) excludes the pre-Alembic perf/uniqueness indexes
   that live in the baseline but not in `models.py`; each is catalogued in
   `docs/dev/alembic-baseline-notes.md`. CI wiring is requested in
   `docs/dev/ci-gates.md`.

## Consequences

| Pros | Cons |
|---|---|
| Revision history + downgrade path | Two schema mechanisms until `updateschema.py` is deleted |
| `alembic check` asserts models-vs-DB in CI | Baseline carries ~20 indexes not in `models.py` (allow-listed, documented) |
| Autogenerate for new changes | Contributors must learn `alembic revision --autogenerate` |
| `updateschema.py` stops growing | — |

## Follow-ups

- CI: fresh-Postgres `alembic upgrade head` + `alembic check` job (see
  `docs/dev/ci-gates.md`).
- Promote the allow-listed indexes into their models' `__table_args__` over
  time, trimming `_BASELINE_ONLY_INDEXES` as each lands.
- Delete `oneirodex/updateschema.py` once every supported install is known to
  be at or past the baseline.
